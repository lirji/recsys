# 企业可靠性后端架构草案

状态：DRAFT / 待计划和契约确认。基线、风险与源码证据见 [评估](../../12-企业级搜推广评估.md)，执行顺序见 [PLAN](PLAN.md)。本文描述目标行为，不代表当前实现。

## 1. 目标、约束和取舍

Brownfield：保留现有模块和 `in-process/grpc` 两种广告调用模式，不新增部署服务。用户已确认客户端可见回执与硬预算预占；其余业务参数见 [待决策清单](PLAN.md#待决策项)。当前 Console 是调试工具，建议默认 sandbox、与正式账务及效果指标隔离。该默认仍需在契约冻结时明确。

目标是五条可验证业务不变量，不是宣称全链路 exactly-once：

1. 响应返回、候选生成、进入实验 control 均不能替代可见曝光回执。
2. 每个有效账户预算日满足 `charged + held <= limit`，三者同币种、同金额精度，不能依赖 Redis 最终保证。
3. 同一资格与合法收费动作最多一个有效收费事实；事件重试和 RPC 重试不产生新收费机会。
4. 对已经在权威数据库提交并回复 accepted 的事件，处理链可恢复、可重放、可核对；承诺不覆盖终端尚未提交的数据或未经演练的整站灾难。
5. 指标和模型评估可追溯到来源、资格、数据窗口、策略/特征/模型版本；测试与旧口径不混入新生产口径。

非目标：新建通用账务中台、拆更多服务、通用 SDK 平台、引入新的 MQ/搜索栈、直接做真实投放切换或生产部署。

## 2. 所有权和事务边界

| 数据 | 唯一写 owner / 物理边界 | 其他模块如何协作 |
|---|---|---|
| 广告目录、素材、广告主配置 | advertiser；现有 ShardingSphere 路由下的目录分片 | 目录变更事件和版本化投影；在线不得直接回写目录 |
| 有效预算、预占、广告资格快照、广告回执、收费/冲正账本、幂等结果、账务 Outbox | `recsys-ad` 中的账务能力，随当前 ad-serving owner 运行；明确 `adDbDataSource` 和专属事务管理器 | advertiser 发送预算命令并查询结果；engine 通过 AdServingGateway 请求；同账户不能同时由两进程当独立余额写权威 |
| 自然内容的交付资格 | rec-engine 的交付用例；使用该 owner 的持久库/事务 | 签名绑定最终 user/item/位置/策略；不直接写 behavior 的事实表 |
| 整次交付操作、冻结条目/位置、各子操作与最终响应结果 | rec-engine 的交付编排 owner，持久化操作状态；广告收费子操作仍归 ad owner | 客户端稳定交付 ID 作用域内恢复整次结果；跨 owner 用幂等命令续办，不声称跨库事务 |
| 自然内容回执与行为事实、对应 Outbox | behavior 自己的数据源和事务 | 验证 engine 签发的资格；持久化接收的不可变上下文；计费广告回执必须先由账务 owner 接受，再投影为分析行为 |
| 目录、行为、账务查询投影 | 各消费者自己的库；Redis 是可重建派生数据 | Inbox/版本条件更新；账务报告以账本为依据，投影必须暴露水位 |
| 流式状态/模型/评估结果 | streaming/offline 各自 owner | 用持久化 checkpoint、不可变制品与输入版本衔接，不另建资金权威 |

**多数据源是首个必须验证的边界。** 即使目录、事件、预算配置落在相同 PostgreSQL 实例，不同 DataSource 也不天然共享同一事务连接。资格、预占、账本、幂等结果和 Outbox 必须在明确的 adDb 本地事务内提交；测试注入每一步失败后检查所有相关库。进程内和 gRPC 模式都走同一用例，不得各写一套账本。

广告主管理页的预算值区分 desired/effective/version。生效额度以账务 owner 确认的命令版本为准。调低额度低于 `charged + held` 时拒绝或安排未来生效，不静默缩小有效上限。暂停广告停止新增资格，已预占义务按批准政策完成/释放。目录分片内 Outbox 与该分片写入同事务；跨分片批量变更用持久化分批任务及版本水位，不假设分布式原子事务。

## 3. 最小交付链路

```mermaid
flowchart LR
  A[候选计算与竞价] --> B[频控资格过滤与最终混排]
  B --> C[稳定操作 ID / 最终广告预占 / 资格签发]
  C --> D[最终结果与不可变交付快照]
  D --> E[客户端可见测量]
  E --> F[同事件 ID 的回执提交]
  F --> G[服务端校验 / 持久化接受]
  G --> H[按计费类型捕获预占 / 唯一账本 / Outbox]
  H --> I[可靠投递 / 幂等投影 / 对账]
```

- 候选计算不再曝光、收费或占预算；频控、GD、DCO、Uplift 的机会与交付统计须分别建模。只有最终广告参与预算预占；预占失败移除该广告，最多做有界补位，不无限重算。
- `operationId` 在重试外生成；资格准备是幂等写命令，不得继续当普通只读重试。一个批次内按固定账户顺序锁定，失败策略与每项结果明确；首版建议单广告资格逐项准备、允许部分广告缺席，未返回的预占走显式释放/到期回收。
- 整次交付操作由 rec-engine 持久化：客户端在显式获取时生成稳定交付 ID，engine 绑定来源/主体/请求摘要，冻结候选快照、条目与位置，并记录确定的子操作 ID、准备结果和最终响应。重复请求先恢复该操作，不能重新召回/混排产生不同收费机会；同 ID 不同请求摘要返回冲突。跨 owner 超时则按子操作 ID 查询/续办，到期转为可查询终态，不用新 ID 掩盖未知结果。
- 最终位置在签资格前冻结；首版预占部分失败时保留自然条目原位置、去掉失败广告留下空位，不自动将已签条目重新编号。若需补位，必须作为签发前的有界计划步骤，尚未返回的旧资格先走确定释放/撤销。V07 验证重试时广告配置/候选池变化仍恢复相同的资格与位置。
- 资格签发后尚不能证明 HTTP 响应到达，统计用“已签发/已返回尝试”，不能把 server issued 标为实际可见。进程在提交后、返回前崩溃时，重试查回原结果。
- 资格绑定服务端确定的主体、环境/发布来源、item/ad、最终 slot、创意版本、实验分配与实际模型版本、计费类型、报价、币种、预算日、到期、测量政策和签名 key/version。客户端不得决定收费金额。
- 推荐缓存复用计算结果，交付签发不缓存复用可收费票据；前端缓存恢复同一响应只重显原资格。显式“重跑”发起新的合法交付操作。
- 自然内容资格和广告资格有不同 owner，统一回执入口可以分发，但批次必须返回逐项结果，不能声称跨 owner 原子接受。

## 4. 资金和生命周期

金额采用精确十进制/定点与显式币种、计价单位；候选方案是 `NUMERIC` + Java `BigDecimal` + JSON 十进制字符串，精度、最大值和舍入点待 D0 决策。禁止在每个 CPM 事件上粗暴取整到分；必须用样例证明多次小额合计与批准的计费规则一致。`double chargedPrice` 的旧字段只能保留兼容报价，不作为新账本真值。

精确金额不能只靠改列类型。ER-S02A 在 `BiddingService` 与账务之间建立规范化定价边界：货币输入从精确金额契约/存储读取；模型概率与排序分数可以保留浮点，但必须按批准的转换规则生成冻结的结算单价、单位与每次最大义务金额。保存输入版本、算法/规则版本、单位换算与舍入版本；NaN、负值、溢出拒绝。旧 double 配置迁移需明确量化规则并核验，不能宣称自动恢复历史精度；未核验数据不进入真实新账本。资格、预占与捕获共用同一冻结价格，不能确认时重跑竞价。

| 状态/动作 | 前置条件与原子效果 | 失败/并发语义 |
|---|---|---|
| 创建 RESERVED | 有效预算命令已生效、资格合法、额度足够；条件更新 held + 创建资格/预占/操作结果 | 重复 operationId 返回原结果；同键不同负载冲突；预算不可判定则不签发新广告 |
| RESERVED → CAPTURED | 对应计费触发合法；尚未过期；唯一事件/业务键；held 减、charged 加、写账本/结果/Outbox | 回执与过期回收锁定同一预占；只允许一个终态；提交后响应丢失查询原结果 |
| RESERVED → RELEASED/EXPIRED | 未捕获，未决合法依赖按到期政策处理；held 减、记录释放原因/事件 | 重复回收无副作用；旧租约不能覆盖已更新状态 |
| 冲正/退款 | 有授权的业务调整指向原账本 | 新增关联流水，不改历史收费事实；是否恢复可用预算另行决策，首版不自动恢复 |

每种计费类型必须指定收费事件：CPM/OCPM 的合格曝光回执；CPC/OCPC 的合格点击；CPA 的经认证且可归因转化。预占金额覆盖该资格在窗口内允许的**最大未决收费义务**，不能用 `pCTR × price` 或 `pCVR × price` 作为硬预算保证。一份资格默认只允许一个已定义收费动作；多次转化收费属于新业务规则，需另定上限和业务键。

先做 CPM 最小闭环，再扩 CPC、CPA。点击早于合格曝光回执时，建议持久化为等待依赖、到期后非计费终止；不伪造曝光，也不让客户端无限等。CPA 长预占影响填充率，必须先确定归因/迟到窗口，未定前不开真实 CPA 新链路。预占已释放后不得无条件补扣；迟到事件可以按明示规则入分析并标非计费，任何补收必须有新的授权和可用预算。

预算日、时区、跨日归属需冻结。候选规则是使用预占创建时的业务日并保持不变，延迟回执结清原义务，不用处理进程的本地日期推断。预算调整、暂停、回收、确认使用确定锁序和条件更新，检查影响行数。

2026-10-15 已实现边界：C02～C10已冻结人民币六位HALF_UP、上海预占日、硬预算与CPM/自然图文政策；C11B按已确认Q-03增加点击内部结算。`ad_click_settlement/receipt/rate/ledger/outbox`仍归原adDb owner，与CPM共享唯一 `ad_budget_account`，没有第二份余额。独立 `click-qualification` 证明、原五分钟期限、可见/点击两个条件、PG同事务风控和一资格一账；锁序为quote→回执唯一键→用户计数→原日账户。S11C1已补齐独立点击可靠投递/Inbox，复用固定事件族的有界传输机制；S11C2补齐独立click-offer及ad/engine检查点、原ID恢复和ADMIN HTTP/可信engine gRPC边界；当前验证与上线状态以ER-S11C2_RESULT为准，没有执行共享环境启用。正式行为与状态见 [C11_DESIGN](C11_DESIGN.md)，迁移/暂停/恢复见 [runbook](SANDBOX_BUDGET_RUNBOOK.md#s11b点击内部结算与到期恢复)。

## 5. 已接受事件的可靠传播

- 每个 owner 的业务写入与自己的 Outbox 同事务；业务键去重时同时能查到原处理结果及待发送事件，不再出现“入库重复所以不补发”。事件有稳定 ID、聚合 ID、聚合版本、schemaVersion、来源和发生/接收时间。
- Relay 有界批次领取、租约和 fencing；在事务外发送 Kafka，收到 broker 确认后条件标记已投递。发送后标记前崩溃允许重复，禁止先标记后发送。退避、重试期限与隔离原因持久化。
- Kafka partition key 按需要有序的聚合确定；不承诺跨分区顺序。消费者将业务效果、Inbox 和版本水位在本地事务提交，再确认消费进度。JSON 解码/落库失败不能吞掉当成功。
- 契约区分完整快照、增量和不可变事实：目录/账户完整快照可按版本覆盖；账本事实按 ledgerEntryId/业务键逐条幂等累加，不能因高版本已到而丢弃较早的合法收费/释放事实。需要连续版本的增量消费者遇到缺口必须暂存/补查并有界追平，不得 latest-wins。多个 relay 即使使用同分区键也可能先发 v3 后发 v2，V12 必须验证两笔金额最终都可对账。
- 数据库投影和 Redis 不能伪称本地原子：先提交权威投影及 Redis 待同步任务，按版本幂等刷新 Redis。墓碑/版本高水位在删除后继续防止旧事件复活；重建包含删除与增量追平。
- 毒消息有界重试后进入持久化隔离区，保留原 ID、版本、负载摘要、失败原因；告警和授权重放按原业务键执行。修复内容生成明确的新修正事件，不能偷偷改同 ID 负载。
- `MAX(id)` 不代表提交顺序；广告日志增量同步改用可靠事件，或重叠扫描与补洞账。存量回填和实时事件并行时需要明确水位/去重。

## 6. 安全、容量、恢复和观测

发布来源认证和用户归属检查先于业务写入；签名包含用途、环境/租户作用域（适用时）、版本、到期和绑定字段。密钥不发浏览器；轮换兼容在途资格，撤销策略有审计。转化回调验证广告主权限与业务事件 ID。日志/trace/历史导出不保存完整票据、Bearer 或敏感个人信息。

数据库/账务依赖故障时停止新增广告资格，自然内容可按独立策略降级；Redis 不可用不能改写资金事实。同步路径设置总 deadline、连接/线程/队列上限；影子计算不挤占主链路，缓存故障回源有预算和并发限制。

核心指标：资格签发、回执接受/拒绝/未知、预占和消费、到期未释放、账务差额、Outbox 最老年龄、隔离积压、消费/投影水位、重建进度、实际 served 模型与数据成熟度。高基数事件 ID 用日志/trace 关联，不作为指标标签。每个告警对应查结果、重发、冻结来源、对账或重建操作。

数据库备份恢复和消息保留各有边界。RPO/RTO、保留期限、容量目标由 D0 记录为业务目标/估算/实测三列，未演练不声称达标。恢复验证必须在隔离目标进行，不能覆盖共享 dev_infra 或生产数据。

## 7. 兼容、迁移与回滚

先扩展数据和版本契约，再 shadow，再按账户/预算日切换唯一收费权威。新旧应用共存期间，不可让同账户一边扣 Redis、一边用 PG 硬预算。旧账务没有可靠基线时先用 sandbox/新测试账户验证，真实账户切换必须有核准的期初预算、已消费和未决义务及对账证据，不从现有异步日志“猜出”余额。

旧 v1 字段号保留，破坏性语义使用新版本或显式能力协商；旧客户端缺资格不能自动进入新计费路径。关新链路的开关停止新增签发，保留账本、Outbox、未决预占和释放任务。代码回退不等于资金回退；禁止回退到 Redis 放行扣费，已收费事实只能业务补偿。

本轮只形成设计。新表、索引、唯一约束、事务入口、迁移版本、契约错误码和运行目标都需由 D0 冻结后进入实施，不能将本文当已上线契约。
