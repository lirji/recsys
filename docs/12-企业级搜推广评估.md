# 12 · 企业级搜推广能力评估

日期：2026-10-15。代码基线：`2dca4b86b8f082d0b07d999943a5c05e7507ed86`。本文记录本轮源码分析和讨论，区分已实现能力、源码风险推断与尚未取得的运行证据；没有执行生产压测、故障演练或账务审计。工作区既有本地运行、容器和权限文档修改不属于本轮交付。

## 结论

项目已经具备较完整的搜推广功能骨架和不少有价值的工程实现：模块化在线链路、多路召回和模型策略、在线离线特征契约、广告竞价、实验分析、内部服务化、可观测与 CI。当前主要差距是**真实曝光到资金、事件、恢复和效果评估之间的业务闭环**，而非算法数量不足。

目前不能仅凭功能表、测试数量或模型名称，认定已经达到企业生产就绪。下一阶段优先落实五个目标：**曝光可信、钱算对、事件不漏、故障可恢复、效果可验证**。详细设计和分阶段候选计划见 [企业可靠性计划](design/enterprise-reliability/PLAN.md)。

用户已确认两项业务决定：

- 以客户端可见曝光回执作为曝光口径，服务端做资格、签名和幂等校验；曝光计费类型在接受合格回执后计费，CPC/CPA 仍须各自的合法点击/转化条件。
- 广告预算采用硬上限：预占后计费，预算不足停止新增投放。

签名只能证明资格来源和绑定信息未被篡改，不能独立证明真人观看或排除作弊；终端尚未提交的观测也不能承诺绝对不丢。

## 三、搜、推、广各自还需要加强什么

### 搜索

[RankService](../recsys-common/src/main/java/com/recsys/common/rank/RankService.java) 接口没有显式 query；[目录检索](../recsys-content/src/main/java/com/recsys/content/AbstractItemCatalogReader.java) 主要使用 PostgreSQL FTS `english` 与既有 query 处理，当前业务以电影为主。应先建设中文检索评测集、query/document 特征、相关性标签、零结果与长尾 query 分析，再根据实测决定是否引入 Elasticsearch。库存、权限、广告预算等权威判断不应迁入搜索投影。

### 推荐

策略扩展丰富，但特征丰富度、线上模型可用率、训练数据来源和真实增益需要单独证明。已有模型版本和数据质量能力应继续使用，补齐模型制品、数据快照、特征版本、实验分配与实际 served 模型之间的追溯。当前缓存命中已重新生成推荐 `exposureId`，缺口是可信资格/最终位置和回执闭环，不能误写为“完全没有曝光身份”。

### 广告

竞价数学、oCPC/oCPM、归因、DCO、Uplift 的代码基础已有，但不能替代账务完整性。优先补齐资金事实、预占状态机、发布来源认证、重复/迟到事件和预算变更。campaign/adgroup、账户结算、多租户配额、审核与素材治理是否深入，取决于目标客户和真实运营流程，不在本轮直接扩建。

GD 的交付计数、频控、DCO 和实验机会也要区分“候选/签发/回执”；尚未定义结算语义的模式不能顺手套用 CPM/CPA 新账本后宣称全覆盖。

## 四、工程证据的边界

- 历史路线中“已落地”是功能与部分验证状态，不代表生产验收。真实 DFM、真实随机 Uplift 和实验样本成熟度等未闭环项继续保留在 [路线 §2.10](07-后续路线执行清单.md)。
- 现有 money-chain gate 主要验证竞价算式与 proto 无损传输；尚不能证明并发硬预算、未知 RPC 结果、跨进程恢复和数据库事务原子性。
- 当前 frontend CI 有 lint/typecheck/Vitest/build，浏览器登录测试不能替代曝光和账务业务验收。Kafka JSON 往返测试不能替代真实 broker/offset 故障验证。
- 告警中已有成功率和 P99 目标，不是实测容量结论。峰值吞吐、热点分布、数据增长、故障 RTO/RPO、恢复水位需记录测量范围和目标负责人后再验收。
- 安全扫描当前采用报告模式；生产准入应明确必须阻断的漏洞/配置条件和例外流程。本轮不升级依赖或修改生产配置。
- 配置缺省、可选权限与开发运行方式不能直接推断某个生产环境已经暴露或已安全；需结合部署事实核验。

## 五、建设顺序与暂不推进项

| 次序 | 建设重点 | 完成的判据 |
|---|---|---|
| P0 | 可信资格、预算/账本、幂等、对象授权、金额单位、RPC 未知结果 | 未展示不因返回而收费；有效预占加消费不越硬上限；重复请求无重复资金效果 |
| P1 | Outbox/Inbox、版本投影、对账、过期回收、重放、资源边界 | 服务端已持久化接受事件可查可补；故障恢复后没有重复账或静默丢失 |
| P1 | 可信曝光分母、真实样本、时间切分、训练/发布门禁 | 数据不合格拒绝训练发布；指标分母、来源、成熟度和模型版本可解释 |
| P2 | 搜索相关性、运营域完善、模型与实验平台、容量隔离 | 以客户流程、瓶颈和收益证据决定范围 |

暂不优先新增更多模型、拆更多服务、替换全套中间件、同时引入另一套 MQ、建设通用调度/工作流平台、默认把 Console 当正式消费者终端。先用现有 PostgreSQL、Redis、Kafka、React 和测试设施证明上述闭环。

## 六、外部机制参考

这些资料说明底层机制，不能替代本项目验证：Java 固定线程池默认使用共享无界队列（[Java 21 Executors](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Executors.html)）；Kafka 与外部存储的端到端语义需要额外协调（[Kafka 3.7 design](https://kafka.apache.org/37/design/design/)）；Flink checkpoint 需要显式配置（[Flink 1.20 checkpointing](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/dev/datastream/fault-tolerance/checkpointing/)）。
