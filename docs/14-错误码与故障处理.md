# 错误码与故障处理

唯一目录为 [`contracts/errors.json`](../contracts/errors.json)。Java `ErrorCode`、`ErrorFamily` 与前端 `api/generated/errorCodes.ts` 由同一生成器生成，禁止分别手改。页面统一显示 `[CODE] 安全提示`；目录记录每项稳定code、文案、HTTP状态及是否是该状态的默认码。当前共256项，8个既有业务HTTP码族。实现及逐片验收见[治理计划](design/error-code-governance/PLAN.md)。

## 用户遇到错误时

| 情况 | 行为与恢复 |
|---|---|
| 401 | legacy清会话并回登录页；OIDC先单飞续期并重试一次，仍失败才清会话。重新登录不能恢复已失效的身份操作 |
| 403 | 显示权限码，保留拒绝；切换正确身份，不能因ADMIN界面可见就绕过服务端权限 |
| 503、超时、网络中断 | 显示固定安全提示；写请求可能已经生效，先按原业务ID查询结果，不创建新ID重复收费 |
| 未知新code、空body、HTML或损坏响应 | 使用当前HTTP状态的安全文案；格式合法的新code可保留供定位，不展示服务端message、SQL或堆栈 |
| 请求主动取消或身份epoch变化 | 保持取消语义，通知入口不弹失败toast；旧身份的回执任务不能继续发送 |
| 实验配置200且ok:false、空/损坏ACK | 显示EXPERIMENT_WRITE_UNCONFIRMED或明确的存储不可用码，不显示成功；重新读取实际配置。逐变体写入可能部分成功 |
| 页面渲染异常 | 显示UI_RENDER_FAILED和重试；修复依赖后刷新或切换路由恢复。开发者控制台诊断不进入页面 |

`WAITING`、`REJECTED`、`DUPLICATE`、HTTP202等正常业务状态继续由原契约解释，不能一律转换成系统异常。页面上的推荐理由、风控规则说明与错误信息不同，仍保留业务语义。

## 协议边界

- HTTP保留`ApiError`的`traceId/code/message/path/fields/timestamp`字段和既有状态分类。服务端未知异常只返回目录文案。前端`toApiError`验证状态与code匹配，只有受限格式traceId可用于排查，不采用任意远端message。已有预算同wireCode的细分提示只允许精确匹配目录候选。
- Java业务主动拒绝使用`PublicErrorException(ErrorCode)`；有内部原因时传cause供服务端诊断。HTTP适配层负责映射；`httpStatus=0`表示本地、作业或对象内码，不可直接作为HTTP状态。原字符串码/兼容别名不重命名。
- gRPC复用`GrpcErrors`，description为目录安全展示、trailer键为`recsys-error-code`。接收方不能仅凭远端trailer信任详情；协议状态单独保留，普通RPC原UNKNOWN不得因文案改造变为可重试状态。内部服务凭据失败与用户业务403分开。
- 前端主动拒绝使用`ClientError`；同步提示用`formatError`；异常转提示用`toApiError`，通知回调用`showApiError`以跳过取消。不能把Error.message、response.data.message、reason或堆栈直接交给页面。
- 诊断、告警、作业状态和实验拒绝等HTTP成功响应中的局部错误仍携带明确状态与目录码。部分失败/缺数据不能显示全成功；客户端必须检查ACK和状态。

## 离线作业

`JobRunner`先检查所有指定作业名，再按原顺序执行。失败输出`[JOB_…]`安全提示并向上传播，不打印“完成作业”；未知失败由`JobFailures`统一转换。无`--job`时仍列出可用作业，不算错误。

读取失败、真实空输入、样本不足、可选模型回退和部分发布各自按目录区分。允许的历史兼容回退仍存在，并给固定提示；故障不能冒充空数据或完成。CSV/多个Redis键/逐物品写入可能已部分生效，失败后先核对产物和实际状态。代码回退不能撤销已写入数据；不要把普通重跑视为原子回滚。

内部日志用于排障，不能转发到公开接口或页面。异常cause可能保留供诊断；本次改造不等同于全面日志脱敏或所有离线作业的事务化。

## 新增或修改错误

1. 确认失败属于哪个业务边界，复用语义准确的既有码；需要新增时编辑目录，保持稳定显式code和可行动文案。不要机械提取显示比例、布局数字或所有正常状态。
2. 运行`python3 scripts/generate_error_codes.py`；同时提交目录及Java/TypeScript生成物。
3. 在真正的公开边界接入，并验证正常路径、失败、取消及未知结果恢复。数据库/Redis事务语义使用隔离真实组件测试；纯Mock不能证明事务正确。
4. 运行`python3 scripts/test_error_codes.py`、`python3 scripts/generate_error_codes.py --check`、`python3 scripts/check_public_errors.py`和受影响模块测试。

CI检查唯一性、HTTP默认映射、码族/别名、生成物一致性与已知公开透传形式。`check_public_errors.py`是有界源码守卫：覆盖JSX/通知直接异常属性以及已修复的实验/登录/渲染入口，不是完整静态污点分析；新出口或变量别名仍须代码审查和行为测试。纯诊断日志和业务reason不列为错误提示。

## 验证边界

浏览器隔离fixture覆盖实际页面对401/403/503、HTML、空body、未知码、网络、坏ACK与渲染异常的处理；真实Redis专项覆盖实验写入失败和部分效果。OIDC续期与回调由既有适配器/组件测试覆盖，不据此宣称已连接真实外部身份提供方。完整资金、自然曝光和混排回执仍以各自真实后端浏览器门禁为准。
